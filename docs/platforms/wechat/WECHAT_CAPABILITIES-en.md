# WeChat Capability Matrix

[中文](WECHAT_CAPABILITIES-ch.md)

This document is a factual index of WeChat host capability status, not a roadmap. Source code and executable Gradle configuration take precedence. A capability may be marked `Stable` only when implementation, automated tests, and the required host-verification evidence exist. See the [WeChat real-host verification matrix](WECHAT_HOST_VERIFICATION-en.md) for environments, procedures, evidence format, and regression frequency.

## Status and verification levels

| Status | Meaning |
| --- | --- |
| `Stable` | The stated scope is implemented and has applicable automated and WeChat Developer Tools verification. |
| `Experimental` | A runnable implementation or proof of concept exists, but its API or behavior is not stable. |
| `Partial` | Only the listed APIs, semantics, or verification levels are complete. |
| `Planned` | Not implemented; an issue or plan is not implementation evidence. |
| `Unsupported` | Intentionally not provided by the current SDK. |
| `P3-Presentation` | A native view or presentation concern outside P1 Host Capability scope. |

| Test Level | Meaning |
| --- | --- |
| `Unit` | Kotlin/JS unit tests or focused adapter tests. |
| `Contract` | The same semantic contract is verified against a reference implementation and WeChat adapter. |
| `Node` | CommonJS smoke or TypeScript checks; this does not prove WeChat runtime compatibility. |
| `DeveloperTools` | Compiled, loaded, and run in WeChat Developer Tools. |
| `RealDevice` | Must be or has been verified on a real WeChat device runtime. |
| `BackendRequired` | Complete verification requires a consumer backend or controlled test service. |

`Minimum Host Version` records the oldest base library that provides the capability, and has three values:

- `Resolved at runtime` — the SDK gates the capability and asks the host through `wx.canIUse` rather than comparing against a recorded figure. The official entry pages for the current Storage APIs, `wx.request`, `wx.getLocation`, `wx.scanCode`, `wx.chooseMedia`, `wx.requestSubscribeMessage`, and the network extension APIs do not state an introduction version for the API itself, so the repository does not infer one from a development machine. This is a live answer for the host actually running, not a missing value.
- A version number — a boundary WeChat documents. The repository records it only where it can cite the source.
- `Not established` — no minimum has been established, either because the capability is not implemented or because the SDK does not gate it.

The SDK reads the base-library version from `wx.getAppBaseInfo` and falls back to the unmaintained `wx.getSystemInfoSync` on base libraries that predate it.

It defines success/fail as valid/expired login state, so the adapter uses the callback itself rather than parsing `errMsg`.
- Observed contract of the WeChat base library shipped with the installed Developer Tools (`package.nw/core.wxvpkg`): `wx.scanCode`'s request option `onlyFromCamera` and the four request categories (`barCode`, `qrCode`, `datamatrix`, `pdf417`); its success fields `result`, `scanType`, `charSet`, `path`, and `rawData`; its result formats (`QR_CODE`, `AZTEC`, `CODABAR`, `CODE_39`, `CODE_93`, `CODE_128`, `DATA_MATRIX`, `EAN_8`, `EAN_13`, `ITF`, `MAXICODE`, `PDF_417`, `RSS_14`, `RSS_EXPANDED`, `UPC_A`, `UPC_E`, `UPC_EAN_EXTENSION`, `WX_CODE`, `CODE_25`); and the dismissal message `scanCode:cancel`, which its simulated path and a cancelled image chooser both produce. This is host-contract evidence rather than a documentation page, which is why this entry records the dismissal classification as a limitation instead of a documented guarantee. That same base library also lists `scope.camera` among its authorization scopes, but nothing in it ties that scope to `wx.scanCode`, so the SDK maps no permission to this capability.
- Observed contract of the same base library for the network extensions: `getNetworkType` enumerates `wifi`, `2g`, `3g`, `4g`, `5g`, `unknown`, and `none`, while `onNetworkStatusChange` carries `isConnected` beside the same set without `5g`; `uploadFile` takes `url`, `filePath`, `name`, `header`, `formData`, and `timeout` and answers with `statusCode` and `data`; `downloadFile` takes `url`, `header`, `timeout`, and `filePath` and answers with `tempFilePath`, `filePath`, and `statusCode`; both task types list `abort`, `onProgressUpdate`, and `offProgressUpdate` (which `RequestTask` does not); and the library's own transfer error mapping produces `<api>:fail timeout`, which is the exact message this SDK maps to a timeout. The library's transfer bookkeeping emits `progress` as a whole percentage beside per-direction byte counts, which is what the progress reader accepts.
- Observed contract of the same base library for `wx.requestSubscribeMessage`: its metadata table declares the option `tmplIds` and a success result keyed by template id with `errMsg` beside it (`"success":{"errMsg":1,"TEMPLATE_ID":1}`). It ships **no implementation and no parameter schema** for this API, so — unlike `wx.scanCode` and `wx.chooseMedia` above — this bundle names no per-template status value and no dismissal message. The only status string observed anywhere in it is `accept`, in a simulated subscription-prompt preview payload (`WxaSubscribeStatusString:"accept"`), which is prompt-rendering data rather than an API result. Only that status is recognized; no dismissal form is classified until a real-host run provides evidence.
- Observed contract of the same base library for `wx.chooseMedia`: its parameter schema (`IChooseMediaOption`) lists `mediaType` as required with the values `image`, `mix`, and `video`, `sourceType` as `album` and `camera`, `camera` as `back` and `front`, `maxDuration` as "3s to 60s, not restricting the album", `count` with no stated maximum, and `sizeType` as an array of strings with no enum of its own. Its simulated implementation reports each `tempFiles` entry with `tempFilePath`, `size`, and `fileType`, adds `duration`, `width`, `height`, and `thumbTempFilePath` only for a video, and reports a dismissal as `chooseMedia:cancel`. `scope.writePhotosAlbum` exists in that library's scope list, but nothing in it ties that scope to `chooseMedia`; the album-saving APIs are not implemented here, so no permission is mapped for this capability.
- Observed contract of the same base library for `wx.requestPayment`: its metadata declares exactly five request fields — `timeStamp`, `nonceStr`, `package`, `signType`, and `paySign` — constrains `signType` to `MD5` and `HMAC-SHA256`, and records an empty success shape, so the callback itself is the whole completion signal and this SDK reads no field from its payload. That library's own payment flow reports an ended interaction as `requestPayment:cancel`, which is the only message this SDK classifies as an interruption; its simulated success path returns the payment backend's `payment_ret` with the `err_msg` prefix rewritten to the API name; ordinary failures are `requestPayment:fail <reason>`. Nothing in that library ties a signature scope or a permission to this API, so the SDK maps none. A real dismissal signal and a real order result need a device with a legal merchant account, which is `BackendRequired`.
- Virtual payment was probed in the same bundle and **is absent from it**. That 18,152,387-byte base library contains `requestPayment` seven times — including its implementation registration and its entry in the `canIUse` metadata table, `"requestPayment":{"object":{"timeStamp":1,"nonceStr":1,"package":1,"signType":["MD5","HMAC-SHA256"],"paySign":1},"success":{}}` — while `requestVirtualPayment`, `virtualPayment` and `VirtualPayment` appear **zero** times, in the metadata table and anywhere else. Adjacent payment names do occur, but only inside the tool's own internal mock lists (`requestOrderPayment` once, `requestApplePayment` twice), which are not API contracts; the two Chinese characters 虚拟 appear only in unrelated tool UI strings. **What this proves:** this Developer Tools runtime contains no discoverable virtual-payment API contract, so the simulator cannot provide positive evidence for the capability. The probe did not execute `wx.canIUse('requestVirtualPayment')`, so no runtime answer is claimed. **What it does not prove:** the behaviour of any real WeChat client, the parameter table, the result shape, the minimum base library version, per-platform availability, or the eligibility rules — an absent entry in a desktop bundle says nothing about a phone runtime. No official page could be retrieved from this environment (fetching `developers.weixin.qq.com` is blocked here, and search returns links only): a search restricted to the official domain lists a page titled `# wx.requestVirtualPayment(Object object)` at `https://developers.weixin.qq.com/miniprogram/dev/api/payment/wx.requestVirtualPayment.html`, queried 2026-09-16. That confirms the API is documented by WeChat and gives its name only; a search result is not contract evidence, so no field list, version or platform matrix is recorded from it. Every detail the Virtual Payment row needs is therefore **to be confirmed** from that page before any implementation.
- [WeChat `wx.getLocation` documentation](https://developers.weixin.qq.com/miniprogram/dev/api/location/wx.getLocation.html): the `type` values `wgs84` and `gcj02`, which the SDK passes through rather than interpreting, and the declarations the host requires before it answers — `app.json.requiredPrivateInfos`, `permission.scope.userLocation`, and the interface permission enabled in the MP backend. No introduction base library version is stated for the API, so the entry relies on `wx.canIUse` rather than a recorded figure. [`wx.chooseLocation`](https://developers.weixin.qq.com/miniprogram/dev/api/location/wx.chooseLocation.html) is deliberately not implemented: its current parameter table exposes no `cancel` callback, so a cancel would arrive as a `fail` and could not be distinguished from a permission denial or a host failure.

Entries marked `Planned` have no implementation in those production sources or exports. Their Tracking value records a Multica gap only; it is not evidence that the capability exists.

## Maintenance rules

1. When a WeChat capability issue is added or closed, review both language versions in the same change.
2. `Stable` requires implementation and specified verification evidence. A class, interface, roadmap entry, or issue alone is only `Planned`.
3. DeveloperTools evidence does not replace RealDevice or BackendRequired evidence.
4. Record a `Minimum Host Version` only from a citable WeChat source, or as `Resolved at runtime` when the SDK gates the capability by asking the host. Never infer a version from a development machine, and never leave a version number without its source.
5. Native UI remains `P3-Presentation`; this matrix must not start Renderer, Compose, Virtual DOM, or WXML work.
