# ADR 0008：权限生命周期边界

[English](0008-permission-lifecycle-boundary-en.md)

- 状态：Accepted
- 日期：2026-09-15

## 背景

SDK 预期要加入的每一项设备能力 —— 定位、扫码、媒体、麦克风、蓝牙 —— 都由用户权限把关，而微信通过 `wx.getSetting`、`wx.authorize` 与 `wx.openSetting` 暴露这道关口。若没有统一的生命周期，这些能力会各自发明一套，同一次拒绝会因为询问的能力不同而报告成不同的结果。

权限有三点与其他能力不同：

- 状态属于用户，不属于 SDK，也不属于某个宿主构建。它可以在小程序运行期间、从程序之外被改变。
- 拒绝不是故障。宿主工作正常，答案是「不」。
- 提示只有在用户手势触发时才正当。自行弹窗的 SDK 是侵扰性的。

## 决策

- **权限生命周期是公共 capability。** `MiniAppPermissions` 报告 `NotRequested`、`Granted`、`Denied` 三态，由 `CapabilityKey("permission")` 标识。它是宿主无关的：`PermissionKey` 命名的是权限「为了什么」，`scope.*` 字符串只存在于微信 adapter 的映射边界内。
- **`Denied` 不是宿主失败。** 拒绝是 `MiniAppException.PermissionDenied`；宿主无法作答是 `MiniAppException.HostFailure`。把两者混为一谈会让调用方去重试一件重试无法解决的事。
- **不做任何缓存。** 每次调用都询问宿主，因为用户随时可以在宿主自身的设置里改变权限，而被记住的答案会在那一刻变成错的。
- **SDK 绝不自行弹窗。** `request` 与 `openSettings` 需要用户手势，且都不会在启动时、也不会作为其他操作的副作用被调用。
- **进入设置页不等于授权。** `openSettings` 在设置页关闭时返回，并报告此后宿主给出的状态。成功返回永远不会被假定为 `Granted`。
- **宿主已有的决定由宿主状态作答。** 已授权的权限不会被再次请求，已拒绝的权限会直接报告为拒绝而不二次弹窗。状态是权威依据，失败消息的形状不是——因此只有明确表示授权被拒绝的消息才会成为 `PermissionDenied`，其余一律保持为宿主失败。
- **未映射的权限是调用方错误。** adapter 未映射的 `PermissionKey` 在任何宿主调用之前就失败，因此任意字符串永远不会被交给 `wx.authorize`。
- **同一权限的并发请求共享一次宿主调用。** 该调用由权限服务拥有，而不是由发起它的调用方拥有，因此取消其中一个调用方不会让其余调用方挂起，也不会被报告为「取消了宿主操作」——宿主本就没有提供取消方式。
- **`PermissionState` 与 `CapabilitySupport.PermissionDependent` 是两回事。** 前者描述权限本身，后者描述某个 capability 当前因权限而受阻。本 capability 自身的可用性由其三个宿主 API 判定，永远不会被报告为依赖权限。
- **权限不包含隐私。** 微信的隐私授权是独立生命周期、独立 API，本决策不实现。
- 不引入弹窗框架、不自动修改设置、不枚举完整微信 scope。只映射某项能力真正需要的权限。

## 后果

- 后续加入的能力复用同一套生命周期，而不必用自己的措辞重述同样的三态。
- 调用方可以区分「用户说了不」与「宿主无法作答」，这对消费者是两条不同的指令：前者请引导用户去设置页，后者可以稍后重试。
- 权限请求必须由消费者自己触发；SDK 不会代劳，完全不请求的消费者只会看到 `NotRequested`。
- 由于不做缓存，一次权限查询就是一次宿主调用。这是「答案不会过期」的代价。
- `Denied` 要求消费者引导用户前往设置页，因为宿主在拒绝之后不会再次弹窗。这是宿主的规则，不是 SDK 的选择。
