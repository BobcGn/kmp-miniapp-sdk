# ADR 0009：隐私授权边界

[English](0009-privacy-authorization-boundary-en.md)

- 状态：Accepted
- 日期：2026-09-15

## 背景

ADR 0008 为 SDK 建立了权限生命周期。微信在系统权限之上还把关另一件事：自基础库 2.32.3 起，小程序必须让用户先同意其隐私协议，之后才能调用已声明的个人信息类接口。低于该基础库时，宿主根本不会拦截这些调用。

这两种条件远看相似，实则不同：系统权限是用户通过操作系统授予应用的，而隐私协议是宿主针对小程序所收集数据提出的自身条件。二者的弹窗、存储与清除都是分开的。把其中一种当成另一种，会让消费者去请求错误的东西。

## 决策

- **隐私是与权限分离的公共 capability。** `MiniAppPrivacy` 由 `CapabilityKey("privacy")` 标识，拥有自己的契约、adapter 与 provider facet。它与 `MiniAppPermissions` 不共享任何状态；任何一方的 adapter 都不得代替另一方。
- **三者分开建模**，因为微信也是分开报告的：可查询的授权要求（`PrivacyStatus`）、一次授权尝试的结果（`PrivacyAuthorizationOutcome`）与 SDK 错误。把它们压进一个枚举，会让一个当下答案看起来像持久状态。
- **`NOT_REQUIRED` 不等于用户已同意。** 微信在用户已同意时返回它，也在小程序未声明任何收集类型时返回它，因此该状态命名的是「宿主的要求」，而不是 SDK 无法证明的「同意」。
- **拒绝是结果，不是异常。** 拒绝隐私协议是正常的宿主结果，因此 `requestAuthorization` 返回 `Refused`，只有宿主层问题才抛错。这与权限生命周期不同——那里拒绝会抛错，因为调用方请求的是它无法缺少的东西。
- **SDK 只报告能够识别的微信拒绝。** 宿主把「拒绝」与「关闭弹窗」送入同一失败回调，且没有提供可区分的字段，因此不存在 `Cancelled` 结果；只有可识别的拒绝消息映射为 `Refused`，未知失败保持 `HostFailure`。
- **前置条件判定点绝不弹窗。** `requireSatisfied` 只查询宿主，并在宿主仍要求同意时以 `PrivacyAuthorizationRequired` 失败。展示弹窗是消费者的职责，必须在用户手势中触发，且绝不在启动时。
- **隐私拥有自己的错误变体。** `MiniAppException.PrivacyAuthorizationRequired` 不是 `PermissionDenied`：两者把消费者引向不同的补救方式。没有隐私 API 的宿主报告 `UnsupportedCapability`，而不是让缺失的函数直接抛错。
- **不做任何缓存。** 宿主的要求会随用户作答与小程序已声明收集类型的变化而变化，因此每次调用都询问宿主。
- **宿主的失败文本只在一处被解读。** 微信没有为隐私拒绝发布稳定错误码，因此由一个 internal mapper 分类失败，并由测试覆盖；原始消息永不进入公共类型。
- 并发请求共享一次宿主调用，因为微信只拥有一个隐私弹窗。该调用由 adapter 拥有而非某个调用方，且不伪造 abort hook：宿主本就没有提供。
- 不实现定位、扫码、媒体、麦克风与蓝牙；只有确实需要该协议的能力才应调用前置条件判定点。

## 后果

- 共享代码可以在不知道障碍是系统权限还是宿主隐私协议的情况下询问「我可以继续吗」，并被告知该解决哪一个。
- 隐私状态不会被误当成权限状态，因此未来的设备能力不会因为检查了另一个而误以为满足了条件。
- 小程序的隐私后台配置与弹窗展示都由消费者负责；SDK 只做告知与把关，从不展示任何界面，也不声称合规。
- 由于宿主不区分「拒绝」与「关闭」，需要区别对待二者的消费者做不到；这一限制来自宿主，而不是 SDK。
